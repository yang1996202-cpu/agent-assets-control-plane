# 产品方法论

本文件记录 Agent Assets Control Plane 演进过程中形成的产品设计与决策方法，
不记录具体实现细节或一次性临时决定。

## 1. 预登记 vs 运行态扫描

- **观察**：让 Agent 预先知道本机装了什么的最佳方式，是让它直接问系统，
  而不是让用户维护一份手动台账。
- **推论**：静态 registry 必然和真实环境脱节，只能作为「历史快照」或「人工备注」。
- **做法**：核心能力转向只读运行态扫描，跑一次、照一次快照，过时就重扫。

## 2. 分类维度必须正交

- **观察**：当 `category` 一个字段同时承载「类型」「形态」「功能」三个维度时，
  标签会爆炸且互相冲突。
- **推论**：需要把主类型（互斥）和形态标签（可选、可多选）分开。
- **做法**：8 个主类型 + 形态标签（cli / app / service / http / stdio）。

## 3. 观测台不操作被观测对象

- **观察**：如果扫描工具会删文件、杀进程、改配置，用户会害怕运行它。
- **推论**：只读观测才能让用户放心按需执行；操作入口必须单独显式触发，
  并有白名单/路径校验。
- **做法**：`asset-runtime` / `asset-macos-signals` 默认只读；dashboard 的
  `kill-process` / `launchctl` 操作有严格的 pid / 路径白名单。

## 4. 面向 Agent 的契约要稳定，面向人的界面要可见

- **观察**：新 Agent 需要知道「X 装在哪」，但不应该每次重新搜索随机 dotdir。
- **推论**：用稳定的文件（`~/AGENT_START_HERE.md`、`AGENT_CONTRACT.md`、
  registry 快照）作为 Agent contract，同时用 dashboard 让人能看得见、审得过。
- **做法**：contract 文件与 dashboard 消费同一份数据，但渲染方式不同。

## 5. 工程实现跟随产品定位收敛

- **观察**：产品定位从「资产登记簿」收敛到「运行态观测台」后，代码组织也应收敛。
- **推论**：dashboard 不应再是单文件大杂烩；公共工具应抽成模块；核心逻辑应有测试。
- **做法**：拆 dashboard 为 data / render / html / api 模块；抽 `lib/agent_assets_common.py`；
  补 `tests/test_*.py`。

## 6. 有状态后台服务启动前必须清理旧实例

- **观察**：调试长周期服务（dashboard、扫描器、监听进程）时，很容易反复启动新实例而
  忘记杀掉旧的，导致多个实例抢端口、抢数据、互相覆盖状态文件，表现就是「状态不刷新」
  「操作记录错乱」「明明停了还显示运行中」。
- **推论**：任何会长期运行的本地服务，启动逻辑必须自带「端口占用检测 + 旧实例清理」，
  而不是依赖外部手动清理或开发者记住 kill。
- **做法**：
  1. 服务启动时先检查目标端口是否被占用。
  2. 确认占用进程是同类服务后，发送 SIGTERM 优雅终止。
  3. 清理完成后再绑定端口、初始化状态。
  4. 日志里明确记录「cleaning up old instance pid=X on port Y」，方便排查。
- **适用场景**：本地 dashboard、后台守护进程、文件锁/状态锁类服务。
