# 产品方法论

本文件记录 Agent Assets Control Plane 演进过程中形成的产品设计与决策方法，
不记录具体实现细节或一次性临时决定。

## 1. 预登记 vs 运行态扫描

- **观察**：让 Agent 预先知道本机装了什么的最佳方式，是让它直接问系统，
  而不是让用户维护一份手动台账。
- **推论**：静态 registry 必然和真实环境脱节，只能作为「历史快照」或「人工备注」。
- **做法**：核心能力转向只读运行态扫描，跑一次、照一次快照，过时就重扫。

## 2. 分类维度必须正交

- **观察**：当 `category` 一个字段同时承载「类型」「形态」「功能」三个维度时，
  标签会爆炸且互相冲突。
- **推论**：需要把主类型（互斥）和形态标签（可选、可多选）分开。
- **做法**：8 个主类型 + 形态标签（cli / app / service / http / stdio）。

## 3. 观测台不操作被观测对象

- **观察**：如果扫描工具会删文件、杀进程、改配置，用户会害怕运行它。
- **推论**：只读观测才能让用户放心按需执行；操作入口必须单独显式触发，
  并有白名单/路径校验。
- **做法**：`asset-runtime` / `asset-macos-signals` 默认只读；dashboard 的
  `kill-process` / `launchctl` 操作有严格的 pid / 路径白名单。

## 4. 面向 Agent 的契约要稳定，面向人的界面要可见

- **观察**：新 Agent 需要知道「X 装在哪」，但不应该每次重新搜索随机 dotdir。
- **推论**：用稳定的文件（`~/AGENT_START_HERE.md`、`AGENT_CONTRACT.md`、
  registry 快照）作为 Agent contract，同时用 dashboard 让人能看得见、审得过。
- **做法**：contract 文件与 dashboard 消费同一份数据，但渲染方式不同。

## 5. 工程实现跟随产品定位收敛

- **观察**：产品定位从「资产登记簿」收敛到「运行态观测台」后，代码组织也应收敛。
- **推论**：dashboard 不应再是单文件大杂烩；公共工具应抽成模块；核心逻辑应有测试。
- **做法**：拆 dashboard 为 data / render / html / api 模块；抽 `lib/agent_assets_common.py`；
  补 `tests/test_*.py`。

## 6. 有状态后台服务启动前必须清理旧实例

- **观察**：调试长周期服务（dashboard、扫描器、监听进程）时，很容易反复启动新实例而
  忘记杀掉旧的，导致多个实例抢端口、抢数据、互相覆盖状态文件，表现就是「状态不刷新」
  「操作记录错乱」「明明停了还显示运行中」。
- **推论**：任何会长期运行的本地服务，启动逻辑必须自带「端口占用检测 + 旧实例清理」，
  而不是依赖外部手动清理或开发者记住 kill。
- **做法**：
  1. 服务启动时先检查目标端口是否被占用。
  2. 确认占用进程是同类服务后，发送 SIGTERM 优雅终止。
  3. 清理完成后再绑定端口、初始化状态。
  4. 日志里明确记录「cleaning up old instance pid=X on port Y」，方便排查。
- **适用场景**：本地 dashboard、后台守护进程、文件锁/状态锁类服务。

## 7. 安装脚本改名时必须同时清理旧名称

- **观察**：当 CLI 工具从旧名称（如 `asset-dashboard`）迁移到新名称
  （如 `agent-assets-dashboard`）时，如果旧二进制还留在 `PATH` 目录里，
  路径解析逻辑或 LaunchAgent plist 很可能继续指向它。用户看到的症状就是
  「代码明明改了，行为还是旧的」「出现奇怪的参数错误」「好像又做了一遍」。
- **推论**：安装脚本不能只写新文件，必须把会与新名称冲突的旧二进制、旧缓存、
  旧备份一起清掉；同时更新 LaunchAgent / 常驻配置指向新路径。
- **做法**：
  1. `install.sh` 里明确列出已废弃的旧名称，安装时 `rm -f` 删除。
  2. 路径解析优先使用新名称，旧名称仅作为兜底 fallback。
  3. 如果本机有 LaunchAgent 常驻服务，install 后检查并提示用户重载，
     或在脚本里直接 `launchctl bootout/bootstrap` 刷新。
  4. 对不再引用的缓存/报告/备份文件也一并清理，避免历史垃圾干扰排查。
- **适用场景**：任何会安装到用户 `~/.local/bin` 且经历过重命名的工具链。

## 9. 本地 dashboard 必须同时防浏览器缓存和旧服务实例

- **观察**：dashboard 是本地静态 HTML + HTTP 服务，用户经常只点浏览器刷新或 F5，
  但浏览器对本地/localhost 页面也可能缓存；同时 LaunchAgent 常驻的 dashboard 进程
  加载的是内存中的旧 lib，不重启示新代码不会生效。两种因素叠加，表现为「我改了代码，
  用户刷新页面却看不到变化」「好像又做了一遍」。
- **推论**：每次交付 dashboard 相关改动后，必须同时做三件事：
  1. 在 HTML/HTTP 层声明禁止缓存；
  2. 把所有「刷新」按钮从 `location.reload()` 改为带时间戳的强制重载；
  3. 重新运行 `install.sh` 并重启常驻 dashboard 服务，确保内存里是最新 lib。
- **做法**：
  1. HTML `<head>` 加 `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` meta。
  2. HTTP 响应头同步加 `Cache-Control` / `Pragma: no-cache` / `Expires: 0`。
  3. 刷新按钮统一用 `location.href = base + '?_t=' + Date.now() + hash`。
  4. 交付后检查端口占用进程启动时间，确认服务已重启；提醒用户关闭旧 tab 再开新页。
- **适用场景**：任何通过本地 HTTP 服务提供 HTML 界面的工具。

## 8. 先审计环境，再修症状

- **观察**：当用户反馈「A 不刷新」「B 状态不对」「C 点了没反应」时，
  如果立刻针对 A/B/C 分别改代码，往往治标不治本；真正原因可能是旧二进制在跑、
  LaunchAgent 指向旧路径、本机配置与代码假设不一致。
- **推论**：接到界面/行为异常反馈时，第一步不是改代码，而是确认「实际在跑什么、
  实际配置是什么、实际输出是什么」。
- **做法**：
  1. 检查当前进程和端口占用：`ps`、`lsof -i :port`。
  2. 检查 LaunchAgent / plist 指向的二进制路径。
  3. 检查 `~/.local/bin`、`~/.local/lib`、`~/.config` 是否有旧版本残留。
  4. 对比「代码期望路径」与「本机实际路径」。
  5. 确认根因后再动手改代码，并把排查结论写进 CHANGELOG/提交信息。
- **适用场景**：任何在真实用户机器上表现与预期不符的 bug。
